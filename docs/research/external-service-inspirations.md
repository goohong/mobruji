# 외부 서비스 영감 분석 — mobruji v0.2~v0.3

> 작성: 2026-05-21 (plan 사이클 10)
> 트리거: 이슈 #136 / PR #140
> 관련: `docs/milestones/v0.2.md`, `docs/features/voice-range-input.md`, `docs/features/recommendation-algorithm-v1.md`
>
> **주의**: 본 문서는 모델 메모리 기반 추정이다. 각 서비스의 최신 UX·기능은 실제 사용자 테스트와 공식 문서로 재검증해야 한다. 차용 후보가 P1/P2로 격상될 시점에 해당 서비스를 별도로 검증한 결과를 본 문서에 갱신한다.

## 목적

v0.2 roadmap(`docs/milestones/v0.2.md`)에서 다음 영역의 기획 영감이 부족하다고 식별되었다.

1. 사용자 음역대 자동 측정 UX (마이크 + pitch detection)
2. 추천 explainability — 현재 `matchReason`이 한 줄 텍스트 한정
3. 소셜/공유 — 즐겨찾기, 듀엣, 도전
4. 진도/성장 시각화 — 사용자가 자신의 음역·취향 변화를 인지

본 문서는 보컬 측정, 음악 추천, 노래방, 학습/게임화 4개 카테고리에서 대중적 서비스 10건을 분석하여 차용 후보를 도출한다.

## A. 보컬 측정 / 훈련

### A-1. Vanido
- **핵심 UX**: 첫 사용 시 마이크로 모음(`아`, `에`)을 발성시켜 사용자의 편안한 음역대(low/high MIDI)를 자동 추정한다. 이후 매일 워밍업 패턴(스케일 상행/하행, 인터벌)을 제시하고 실시간 pitch tracker로 정확도를 시각화한다(목표 음 vs 발성 음).
- **mobruji 차용 후보**: v0.1 음역대 수동 입력(`voice-range-input.md`)을 보완하는 **음역대 자동 측정 페이지**. 짧은 발성(5~10초) → Web Audio API + pitch detection(YIN/CREPE 등) → `lowMidi/highMidi` 후보 산출 → 사용자가 확인 후 저장.
- **차별화 포인트**: Vanido는 *훈련*이 1차 목적이라 매일 사용 동기를 학습 streak로 잡지만, mobruji는 *노래방 추천*이 1차 목적이므로 측정은 **1회성 온보딩**으로 짧게 끝낸다. 추천 결과 페이지에서 "현재 음역대로 다시 측정하기" 진입점만 노출하는 식.

### A-2. Smule
- **핵심 UX**: 노래방 + SNS 결합. 원곡 위에 사용자 보컬을 녹음, 다른 사용자와 듀엣 가능. 실시간 pitch 가이드라인(스크롤되는 미디 노트)을 따라 부르고, 정확도 점수가 즉시 표시된다.
- **mobruji 차용 후보**: (v0.3+) **듀엣/공유 모드**. 추천 받은 곡을 친구에게 "이 곡 같이 부르자" 공유, 단톡방 단위 추천 모드(여러 사람 음역대 교집합으로 곡 추천)도 자연스러운 확장. 단기적으로는 추천 결과 카드의 **공유 버튼**(카카오톡 링크 공유)만 가벼운 1차 단계.
- **차별화 포인트**: Smule은 in-app 녹음·송출이 핵심이라 무거운 미디어 파이프라인이 필수다. mobruji는 *실제 노래방 가는 사람*이 타겟이므로 in-app 녹음은 over-engineering. **곡 정보 공유 + 모임 단위 추천**까지만 차용.

### A-3. SingPlay
- **핵심 UX**: 임의의 오디오 파일에서 보컬 트랙을 분리(Spleeter 기반)하여 MR(반주) 트랙을 즉석 생성. 사용자가 자기 곡을 가져와 노래방처럼 사용한다.
- **mobruji 차용 후보**: 자체 곡 분석 파이프라인(`song-self-analysis-pipeline.md`)과 직접 겹친다. SingPlay의 production-grade Spleeter 사용 경험은 mobruji 자체 분석 PoC(`v0.2 1-1`)의 품질 벤치마크로 활용 가능. 사용자 노출 UX는 차용 후보 아님.
- **차별화 포인트**: SingPlay는 사용자 입력 파일이 1차, mobruji는 큐레이션 100곡이 1차. 파이프라인은 유사하나 *입력 경로*가 다르므로 사용자 UX 차용 X.

## B. 음악 추천 + Explainability

### B-1. Spotify
- **핵심 UX**: Discover Weekly(주간 30곡), Daily Mix(취향 클러스터별 무한 재생), Release Radar(신곡). 각 추천에 "Why this song?" 컨텍스트(예: "당신이 자주 듣는 X 아티스트와 비슷한 분위기")가 카드 형식으로 펼쳐진다. 내부적으로 audio features(tempo, energy, valence, danceability) + 협업 필터링 + NLP 기반 가사 분석을 혼합.
- **mobruji 차용 후보**: **`matchReason` 카드 확장**. 현재 한 줄 텍스트 → 다중 라인 구조화 카드로 강화. 예시: "음역대 일치(C3~E5 중 C4~D5 사용)", "선호 분위기와 일치(차분함)", "최근 부른 곡과 유사 BPM". 추천 결과 UI에서 카드 펼치기 인터랙션으로 노출.
- **차별화 포인트**: Spotify는 *듣기* explainability라 청취 이력이 풍부하지만, mobruji는 사용자 액션이 적다(추천 응답만). **음역대 매칭은 정량 근거가 명확**한 강점이므로 그 부분을 1순위로 시각화(예: "당신 음역 C3~E5 / 곡 음역 D3~D5 → 100% 포함"). 협업 필터링 영감은 1-7(피드백 영속화) 이후로 미룬다.

### B-2. 멜론 / 지니 / 벅스
- **핵심 UX**: 한국 차트(실시간/일간/주간), 사용자 청취 기반 "당신을 위한 플레이리스트", 노래방 차트(멜론은 별도 노래방 인기곡 섹션 운영). 장르/시대/분위기 필터링이 풍부하다.
- **mobruji 차용 후보**: **시드 100곡 큐레이션**(`song-curation-seed-100.md`) 선정 시 멜론 노래방 차트 + 지니 인기차트 교차로 가중치 부여. UI 차용 후보로는 분위기/장르 필터(이미 v0.1에 `mood` 필드 존재 — 표현만 강화).
- **차별화 포인트**: 멜론은 *전국민 차트* 단위, mobruji는 *개인 음역대 적합도* 단위. 차트 기반 추천은 mobruji의 보조 시그널(인기도)로만 사용해야지 1차 시그널이 되면 음역대 적합도가 흐려진다.

### B-3. Apple Music
- **핵심 UX**: 인간 큐레이터(에디터)의 플레이리스트 + 알고리즘 추천 hybrid. "For You" 탭에 "Made for You" + "Apple Music 1 라디오 DJ 큐레이션"이 공존. 추천 사유는 Spotify보다 가볍게("Inspired by X").
- **mobruji 차용 후보**: **인간 큐레이션 + 알고리즘 hybrid 패턴**. v0.2 시드 100곡 큐레이션이 이미 인간 큐레이션 자산이다. v0.3+에서 사용자 피드백(1-7) 데이터가 쌓이면 알고리즘 가중치 도입, 큐레이션 라벨(예: "에디터 추천")을 추천 카드에 명시.
- **차별화 포인트**: Apple은 글로벌 음악 전체가 대상, mobruji는 노래방 부를 수 있는 곡 한정. 큐레이션 라벨도 *부르기 좋은 곡 가이드*(예: "남자 미디엄 음역 추천", "여자 고음 도전곡")로 노래방 도메인 친화로 재구성.

## C. 진도 / 성장 / 게임화

### C-1. Yousician
- **핵심 UX**: 악기(기타/피아노/우쿨렐레/보컬) 학습 앱. 실시간 마이크 입력으로 사용자 연주를 판정하고, 레벨/스킬 트리(코드/리듬/이어 트레이닝)별 진도를 시각화. 매일 도전(daily quest) + 주간 골 + 학습 streak.
- **mobruji 차용 후보**: **사용자 음역 발전 추적**. v0.1에서 음역대를 한 번 입력하면 끝이지만, 측정 페이지(A-1)를 1회성이 아닌 *주기적 재측정* 기능으로 확장하면 "지난달 대비 high MIDI +2 상승" 같은 성장 시그널을 제공할 수 있다. 추천 history page(이슈 #134 추정)와 결합하면 "지난주 추천 30곡 중 12곡이 새 음역대로 가능해짐" 같은 카피.
- **차별화 포인트**: Yousician은 *훈련*이 1차라 매일 사용을 게임화로 강제하지만, mobruji는 *노래방 가기 전 검색*이 1차라 매일 사용 강제는 부적합. **성장 시각화는 알림이 아닌 회고형 카드**(앱 진입 시 "지난달 음역대 변화" 같은 모듈)로 자연스럽게 노출.

### C-2. Duolingo
- **핵심 UX**: 언어 학습. streak(연속 학습일), XP, 리그(주간 랭킹), 하트 시스템(오답 패널티), 도전 알림 푸시. 학습 패턴 게임화의 사실상 표준.
- **mobruji 차용 후보**: **가벼운 streak / 도전 후보**. 단, mobruji 도메인 적합도 낮음. 굳이 차용하면 "이번 달 부른 곡 N개" 회고 카드 정도. 푸시 알림으로 매일 호출하는 패턴은 도메인 부적합(사용자가 노래방 갈 때만 열면 된다).
- **차별화 포인트**: 차용 시 가장 가벼운 형태로만 — **연속 일수가 아닌 누적 부른 곡 수**(`RecommendationHistory.markedAsSung` 같은 신규 필드 가정)로 회고 카드 구성. push 알림은 v0.3에서도 비활성.

## D. 노래방

### D-1. TJ미디어 / 금영 공식 앱
- **핵심 UX**: 노래방 기기 제조사가 직접 운영. 곡 번호 검색이 핵심 진입점. 인기곡/신곡 차트, 즐겨찾기, 부른 곡 기록(예약 송출/QR 송출 기능 일부 모델). 추천은 약함(차트 단위가 사실상 전부).
- **mobruji 차용 후보**: **TJ/금영 곡 번호 표시**. mobruji 추천 결과 카드에 TJ/금영 곡번호를 함께 노출하면 사용자가 실제 노래방에서 즉시 입력 가능 — 진정한 도메인 적합 디테일. `Song` 엔티티에 `tjNumber/kyNumber` 필드는 이미 가정되거나 추가 가치 있음.
- **차별화 포인트**: TJ/금영은 *기기 ↔ 앱*이 본업이라 추천이 약하다. mobruji는 *추천*이 본업이라 곡 번호는 **사용자 핸드오프 디테일**로 차용 — 결국 사용자가 노래방에서 곡을 입력하려면 번호가 필요하다.

### D-2. SongPop
- **핵심 UX**: 음악 퀴즈 게임. 곡 일부 듣고 제목/가수 맞히기, 멀티플레이어 대결. 노래방과 직접 관련 없지만 *친구 초대 + 점수 경쟁 + 곡 발견* 메커닉이 강하다.
- **mobruji 차용 후보**: (v0.3+) **친구 초대 + 모임 단위 추천**. SongPop의 친구 대결 메커닉을 mobruji 도메인에 맞게 변환 → "노래방 모임 만들기 → 4명 음역대 교집합 → 모두 부를 수 있는 곡 추천". A-2(Smule 듀엣)의 가벼운 버전이자 가장 노래방 친화적 응용.
- **차별화 포인트**: SongPop은 *맞히기*가 핵심이라 곡을 짧게 들려준다(저작권 30초). mobruji는 곡 전체를 부르는 게 목적이므로 게임화는 *맞히기* 대신 *함께 부르기 후보 선정*으로 재구성.

## F. v0.2 roadmap 추가 권장 후보

본 분석 결과 v0.2 또는 v0.3 진입 가치가 있는 신규 후보는 다음과 같다. 본 PR 범위에서는 *후속 이슈 제안*까지만 다루고, 실제 roadmap 추가·spec 신설은 별도 PR로 진행한다.

### F-1. [P1 후보] 음역대 자동 측정 페이지
- **신규 spec 제안**: `docs/features/voice-range-auto-measurement.md`
- **요약**: Vanido 패턴 차용. 짧은 발성(5~10초) → Web Audio API + pitch detection → `lowMidi/highMidi` 후보 산출 → 사용자 확인 후 저장. 1회성 온보딩 + 추천 결과 페이지에서 "다시 측정하기" 진입점.
- **의존**: pitch detection 라이브러리 ADR(YIN vs CREPE vs aubio.js 등), 마이크 권한 UX, 측정 정확도 검증 데이터셋.
- **우선순위 근거**: v0.1 수동 입력 UX(`voice-range-input.md`)의 가장 큰 사용자 마찰. v0.2 P1 격상 가치 있음. 단 v0.2 기존 P1 4건(1-1~1-4)이 이미 be 5~6 사이클을 차지하므로 v0.2 후반 또는 v0.3 초반 진입이 현실적.

### F-2. [P2 후보] 추천 explainability 강화 — `matchReason` 다중 라인 카드
- **기존 spec 갱신 제안**: `docs/features/recommendation-algorithm-v1.md` §matchReason
- **요약**: Spotify "Why this song?" 패턴 차용. 현재 한 줄 텍스트를 구조화된 다중 신호(`voiceRangeMatch`, `moodMatch`, `tempoMatch`, `popularitySignal`)로 분해. 응답 DTO에 `matchSignals: List<MatchSignal>` 추가.
- **의존**: 추천 알고리즘 시그널 분해(현재 단순 음역대 포함 검사 → 다중 시그널), fe 카드 펼침 UX.
- **우선순위 근거**: 사용자 신뢰 향상 효과 크고 backend 작업량은 중간. v0.2 1-5(곡 상세 UX) 진행 중인 fe 사이클 9와 자연스럽게 연결.

### F-3. [P2 후보] 추천 카드에 TJ/금영 곡 번호 노출

- **요약**: 노래방 도메인 핵심 디테일. 추천 → 사용자가 노래방에서 즉시 입력 가능한 정보(번호) 핸드오프.
