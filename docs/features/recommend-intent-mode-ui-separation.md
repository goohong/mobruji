# 추천 결과 페이지 의도 모드 UI 분리·정제

> 본 spec 은 `recommend-page-visual-ux-audit-1708.md §2 A-2`("유사 스타일 모드 컨트롤 3종이
> 위계 없이 나열")가 박제한 시각 갭의 **의도 모드 부분만** 떼어 해소하는 후속 설계다. 1차 대응이던
> `RecommendModeGroup` 분리(#1712 — 필터는 결과 위, 모드 진입은 결과 아래)에도 의도 모드 토글이
> 결과 목록과 같은 위계로 경쟁하는 문제가 남아, 진입 UI 를 한 방향으로 정제·합의한다. 동시에 본 spec 은
> `persona-expansion-social-emotional.md §8 Q2`(페르소나 모드 진입 — 온보딩 통합 vs 추천 화면 내 모드
> 선택)가 "fe 구현 spec" 으로 미뤄 둔 결정을 닫는 **그 fe 구현 spec** 이다. 추천 알고리즘·엔드포인트·
> 결과 카드 시맨틱은 **무변경** — 진입 UI 위계만 바꾼다.

## 1) 개요 (What / Why)

- 대상 액터: `/recommend` 추천 결과 페이지에 도달한 모든 사용자(P-E 안전곡 / P-F 과시 / P-G 듀엣 의도를
  가진 사용자 포함).
- 문제: 결과 페이지의 의도 모드 진입(`IntentModeToggle` — "안 망할 곡" / "고음 질러 박수받기" /
  "둘이 함께 부를 곡" 3 토글)이 결과 카드·필터와 동일한 둥근 표면·굵은 라벨의 비주얼 무게로 나열돼,
  "결과 페이지" 인데 선택 UI 가 화면 위계를 점령하고 "이동 vs 모드 전환 vs 좁히기"가 시각적으로 구분되지
  않는다(`recommend-page-visual-ux-audit-1708.md §2 A-1/A-2`).
- 본 spec 은 **선행 데이터 의존도 분석**(§5-2)으로 "의도 모드 전환이 결과를 어떻게 변동시키는가"를 먼저
  확정하고, 그 결론에 맞춰 세 방향(진입점 이동 / 필터 칩 강등 / 2-step 모달)을 비교(§5-3)해 **권장안과
  fe 구현 범위**(§4, §5-6, §6)를 못 박는다. 코드 구현은 본 spec 합의 후 fe 사이클이 수행한다.

## 2) 사용자 시나리오

1. **(결과 먼저 본 뒤 모드 전환)** 사용자는 음역대만으로 나온 기본 추천 결과를 먼저 훑고, "오늘은 안 망할
   곡 위주로 보고 싶다" 싶을 때 결과 아래 **"다른 방식으로 추천받기" 단일 진입**을 눌러 모드 선택 surface 를
   연다. 안전곡을 고르면 결과가 안전곡 피드로 바뀌고, 결과 상단에 "의도 모드: 안전곡(해제)" 가벼운 배지가
   뜬다.
2. **(듀엣 — 추가 입력 필요)** 연인이 "둘이 부를 곡" 모드를 고르면, 같은 surface 의 다음 단계에서 파트너
   음역·성별을 입력하고 듀엣 추천 + 파트 분배 결과를 받는다. (현행은 토글 ON 후 결과 피드 안에서 파트너
   패널이 다시 뜨는 2단 노출 — 본 spec 은 이를 한 surface 의 step 으로 합친다.)
3. **(모드 미사용 — 기본 사용자)** 의도 모드를 모르는/원치 않는 사용자는 결과 페이지 첫 화면에서 결과
   카드를 더 빨리 만난다. 모드 진입이 단일 2차 액션으로 강등돼 결과 위계를 가리지 않기 때문이다.

## 3) 요구사항

### 기능 요구사항
- [ ] 결과 아래 `IntentModeToggle` 3개 인라인 토글을 **단일 2차 진입(CTA)** 으로 강등한다 — 결과 목록과
      같은 위계로 경쟁하지 않게.
- [ ] 단일 진입을 누르면 **모드 선택 surface(2-step 바텀시트, §5-6)** 가 열린다: step 1 = 의도 모드 선택
      (안전곡 / 과시 / 듀엣 / 미선택=기본), step 2 = 모드별 추가 입력(듀엣만 파트너 음역·성별; 안전곡·과시는
      step 1 선택 즉시 적용).
- [ ] 모드 적용 후 **활성 모드 신호**: 결과 상단(또는 진입 CTA)에 "의도 모드: <라벨>" + 해제 어포던스를
      가볍게 노출해, 모드가 켜졌음을 결과 위계에서 인지하게 한다.
- [ ] 모드 미선택 = 현행 default 추천(하위호환, 결과 화면 불변).
- [ ] 호스트 모드(`/recommend/host` 페이지 이동)는 의도 모드와 성격이 다르므로(이동 vs 모드 전환) **시각적
      으로 분리 유지** — 시트 안 "새 화면(›)" 행으로 함께 묶거나 현행 이동 링크를 그대로 둔다(§8 Q2).

### 비기능 요구사항
- **추천 데이터 흐름 무변경** — `selectedPersona` 상태·쿼리 분기·전용 엔드포인트(`/safe`·`/showoff`·
  `/duet`)·결과 카드 시맨틱은 그대로. 본 spec 은 진입 UI 만 바꾼다 → 결정성·p95 회귀 가드
  (`recommendation-p95-regression-guard.md`)·BE 무영향.
- **결과 우선 노출**(#1711 상속) — 첫 화면에서 결과 카드가 더 빨리 보여야 한다.
- **접근성** — 시트 열림/단계 전환은 키보드 포커스 트랩 + `aria-pressed`/status live region(기존
  `SongDetailSheet`·`IntentModeToggle` 패턴 준수). 모드 상호 배타 시맨틱 유지.
- **회귀 0 (모드 미선택 경로)** — 모드를 켜지 않은 사용자의 결과 화면 동작은 변하지 않는다.

## 4) 범위 / 비범위 (중요)

### 포함
- 의도 모드 진입 UI 의 위계 분리·정제(3 토글 → 단일 CTA → 2-step 시트) 설계.
- 모드별 추가 입력(듀엣 파트너) 을 시트 step 으로 통합하는 흐름 설계.
- 활성 모드 신호(결과 상단 배지/해제) 설계.
- `persona-expansion-social-emotional.md §8 Q2` 의 진입 방식 결정(=on-page 시트, 혼합) 확정.

### 제외 (Out of Scope)
- **추천 알고리즘/엔드포인트/결과 카드 시맨틱 변경** — 본 spec 은 진입 UI 위계만. 신호·산식·가중치 무변경.
- **온보딩 `PersonaEntryPath` 통합**(persona §8 Q2-a) — 온보딩 첫 화면에서 페르소나를 고르게 하는 진입
  확장은 별 트랙(부모 persona spec + `first-user-onboarding-flow.md`). 본 spec 은 "결과 페이지에 도달한 뒤"
  의 의도 모드 진입만 다룬다.
- **호스트 모드 시퀀스 화면 재설계** — `/recommend/host` 의 도입·고조·마무리 시퀀스 자체는 별 spec.
- **분위기/나이대/성별 필터(RefinePanel) 재설계** — 데이터 성격이 다른(같은 엔드포인트 좁히기) 필터는
  결과 위 접이식 패널(#1712)을 유지. 본 spec 은 의도 모드만 손댄다.
- **정렬/뷰 토글(sortKey/viewMode) 위치 변경** — 클라이언트 처리(서버 무호출)라 결과 헤더 인라인 유지가
  적절. 본 spec 비범위.

## 5) 설계

### 5-1) 도메인 모델
- 신규 BE 엔티티·신규 도메인 용어 **없음**. 기존 재사용(이미 `06-domain-model.md §4` 등재):
  - `RecommendationPersona`(`recommendation`) — `P-E` 안전곡 / `P-F` 과시 / `P-G` 듀엣. 진입 UI 가 고르는
    의도 라벨(영속 엔티티 아님).
  - `PersonaEntryPath`(`user`/web) — 온보딩 진입 분기. 본 spec 의 on-page 시트와는 **별 surface**(§4 비범위).
- 본 spec 은 신규 용어를 도입하지 않으므로 `06-domain-model.md §4` 변경 없음.

### 5-2) 데이터 의존도 분석 (선행 점검 — 권장안의 근거)

결과 페이지의 사용자 조작은 **데이터 영향이 셋으로 갈린다**(`web/app/recommend/page.tsx` 코드 근거):

| 조작 | 데이터 영향 | 근거(코드) |
|---|---|---|
| **정렬**(`sortKey`: 추천순/음역 적합순/분위기 적합순) | **클라이언트 재정렬만**(서버 무호출) | `sortedRecommendations` `useMemo` — 이미 로드된 목록을 축 기준 재정렬 |
| **분위기·나이대·성별 필터**(RefinePanel) | **서버 재요청**(같은 default 엔드포인트 좁히기) | `recommendQuery` `queryKey` 에 `selectedMood/AgeGroup/Gender` 포함 → 첫 페이지부터 재발화. `POST /api/v1/recommendations` 에 파라미터만 추가 |
| **의도 모드**(`selectedPersona`: 안전곡/과시/듀엣) | **다른 엔드포인트로 서버 재요청 + 다른 결과 시맨틱 + (듀엣) 추가 입력** | persona 선택 시 default 무한스크롤 쿼리 `enabled=false`(중복 페치 방지), 전용 단일샷 피드(`SafeRecommendationFeed`/`Showoff`/`Duet`)가 `/recommendations/safe`·`/showoff`·`/duet` 페치. 결과 카드에 `safetyReason`/`killingPartReason`/파트 분배 등 **모드 전용 필드**. 듀엣은 **파트너 음역·성별 추가 입력 패널** 필요 |

**결론(핵심):** 의도 모드 전환은 "필터/정렬"이 아니라 **추천 모드(엔드포인트) 전환**이다. 분위기 필터(같은
엔드포인트 좁히기)·정렬(클라이언트)과 **데이터 위계가 근본적으로 다르다.** 따라서:

- 의도 모드를 분위기 칩과 한 줄에 섞으면(Option B) **데이터 의미가 오인된다** — 가벼운 좁히기처럼 보이나
  실제론 엔드포인트·결과 종류가 바뀌고, 듀엣은 추가 입력이 필요하다. 칩 한 칸에 담기지 않는다.
- 의도 모드는 무거운 모드 전환이므로 **전용 focused surface** 를 주는 것이 데이터 성격과 정합한다.
- 정렬·필터는 현행 위치(결과 헤더 인라인 / 결과 위 접이식)가 데이터 성격상 적절하므로 건드리지 않는다.

이 데이터 결론이 fe 구현 범위(진입점 위치)를 가른다 — 의도 모드만 시트로 승격 분리.

### 5-3) 방향 비교 (3안) — 데이터 의존도 기준

| 방향 | 데이터 성격 정합 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| **A. 진입점 이동**(결과 페이지 밖 / 결과 전 모드 선택 단계로 이전) | 높음(무거운 전환을 deliberate 진입으로) | 결과 페이지 단일 목적화, 위계 경쟁 완전 제거 | 결과를 본 뒤 "안전곡으로 한 번 바꿔보기" 즉석 탐색 상실(#1712 가 의도적으로 결과 아래 2차 액션으로 보존한 가치). 듀엣 파트너 입력 진입 흐름 재설계 부담 | **부분 채택** — 단, 온보딩 진입 통합은 persona §8 Q2-a 별 트랙 |
| **B. 필터 칩 강등**(RefinePanel 안 분위기 칩과 동렬) | **낮음(오인 유발)** | 시각적으로 가장 컴팩트 | 엔드포인트·결과 시맨틱이 바뀌는 모드를 "같은 엔드포인트 좁히기 칩"으로 위장. 듀엣 파트너 입력이 칩에 안 맞음. 모드별 결과 헤더(relaxed/안심 포인트)와 충돌 | **기각** |
| **C. 2-step 모달/바텀시트**(단일 2차 CTA → 시트에서 모드 선택 + 모드별 입력) | 높음 | 결과 위계 경쟁 제거(3 토글 → CTA 1개). 시트가 듀엣 파트너 입력 공간 제공. 결과 본 뒤 on-page 즉석 전환 유지. 모드 설명 공간 확보 | 시트 여는 탭 1회 추가 | **권장(primary)** |

**권장안 = C(2-step 바텀시트).** 데이터 의존도 결론이 직접 가리킨다: 의도 모드는 엔드포인트가 바뀌는
무거운 전환이라 **전용 surface** 가 맞고(→ B 기각: 칩 위장은 오인), 동시에 #1712 가 보존한 "결과 본 뒤
즉석 모드 전환" 가치를 지키려면 on-page 여야 한다(→ A 의 결과-밖 이동은 부분 채택에 그침). C 는 둘을
모두 만족하며 듀엣 추가 입력 step 까지 한 surface 로 자연스럽게 흡수한다. 이는 `persona-expansion §8 Q2`
를 **(c) 혼합**(on-page 진입을 유지하되 경쟁 인라인 토글이 아니라 deliberate focused surface) 으로 닫는다.

### 5-4) 데이터 흐름 / 시퀀스
```
[추천 결과 페이지 — 기본 추천(음역대만)]  ← 결과 우선, 의도 모드는 단일 2차 CTA
   │
   └─[탭: "다른 방식으로 추천받기"]
        ▼
   [의도 모드 시트 — step 1: 모드 선택]  안전곡 / 과시 / 듀엣 / (다시 누르면) 해제
        │                                    │
        │ (안전곡·과시 선택 즉시 적용)         │ (듀엣 선택)
        ▼                                    ▼
   [시트 닫힘 → 결과 = 모드 피드]        [step 2: 파트너 음역·성별 입력]
        │                                    ▼
        │                              [시트 닫힘 → 듀엣 결과 + 파트 분배]
        ▼
   [결과 상단 "의도 모드: <라벨>(해제)" 배지]
```
- 진입 UI 만 바뀌고, 모드 선택 후 데이터 경로(`selectedPersona` 분기 → 전용 엔드포인트 피드)는 현행 그대로.

### 5-5) DB 마이그레이션
- 없음. BE 변경 없음.

### 5-6) 프론트엔드 화면
- 변경/신규(설계):
  - `RecommendModeGroup` 축소 — 3개 인라인 `IntentModeToggle` 버튼을 제거하고 **단일 2차 CTA 버튼**("다른
    방식으로 추천받기")으로 대체. 호스트 모드 이동 행은 시트로 흡수하거나 현행 유지(§8 Q2).
  - 신규 `<IntentModeSheet>` — 기존 `SongDetailSheet`(바텀시트 패턴) 재사용. step 1 = 모드 picker(기존
    `IntentModeToggle` 의 모드 카피·`RecommendationPersona` 매핑·상호 배타 로직 재사용), step 2 = 듀엣 파트너
