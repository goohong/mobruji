# 노래방 곡번호 자동 수집 파이프라인 검토 (karaoke-number-auto-collection)

## 1) 개요 (What / Why)

- 사용자 directive (2026-06-03, directive `1511636168100544734`): TJ/금영 등 외부 노래방 곡목을 **자동 수집**해 곡 데이터를 적재하는 파이프라인 도입을 검토한다.
- 본 spec 의 핵심 결정 대상은 **노래방 곡번호 (`tjNumber`/`kyNumber`) 의 자동 수급 경로** — 곡 일반 메타데이터(제목/아티스트/연도/장르)의 합법 수급은 이미 [[song-catalog-expansion]] 가 SoT 로 결정했으나, **노래방 곡번호는 어떤 CC0 출처(MusicBrainz/Wikidata)도 제공하지 않아** 현재 `song-curation-seed-100.md §4` 에서 "ADR/이슈 #70 (v0.2 보류), tjNumber/kyNumber 는 _가능 시_ 수기" 로만 처리되고 자동 경로가 미설계 상태다.
- 본 spec 은 그 공백을 메운다: (1) 곡번호 수집 방식 비교(크롤링 vs 공개 데이터/API vs 수기), (2) TJ/금영 사이트 약관·robots.txt·저작권·**DB제작자권** 리스크 판정, (3) v0.2 자체 분석 pivot 과의 정합성, (4) 도메인 영향, (5) 채택 시 파이프라인 아키텍처, (6) 단계적 로드맵을 박제한다.
- 새 외부 연동 + 다중 PR 가능성 + 곡번호 신뢰성 책임을 동반하므로 Feature Spec 선작성 대상 (CLAUDE.md §4).
- 대상 액터: 시스템(수집 배치) + 운영자(검수). 사용자 직접 화면 없음 — 곡번호가 채워진 곡이 기존 추천/검색/카탈로그 경로로 노출되는 간접 효과(노래방에서 바로 입력 가능).

> **경계 (중복 방지)**: 곡 *메타데이터* 카탈로그 확장의 SoT 는 [[song-catalog-expansion]], 음역대 추출은 [[song-self-analysis-pipeline]], 수기 큐레이션은 [[song-curation-seed-100]] 이다. 본 spec 은 그 세 spec 이 다루지 않는 **노래방 곡번호 차원**만 책임지며, 크롤링 비채택 기조를 [[song-catalog-expansion]] §5-3 으로부터 상속·심화한다.

## 2) 사용자 시나리오 (시스템 / 운영)

사용자 직접 화면 없음. 운영·시스템 시나리오:

1. **곡번호 공백 식별** — 시드/임포트로 들어온 곡 중 `tjNumber`/`kyNumber` 가 NULL 인 곡 목록을 운영자가 조회한다.
2. **합법 경로 수급** — 운영자가 (채택안에 따라) TJ/금영 공식 곡목 검색을 _수기_ 로 확인해 곡번호를 (title, artist) 와 매칭하거나, 합법 데이터 출처가 확보되면 배치가 곡번호를 채운다.
3. **정규화·중복 제거** — 같은 곡의 TJ/금영 번호를 표준 형식(숫자 문자열)으로 정규화하고, (title, artist) 기준으로 곡에 멱등 매핑한다.
4. **운영자 검수** — 동명이곡/리메이크/라이브 버전 등 매칭 모호 곡은 운영자 검토 큐로.
5. **적재** — 검증된 곡번호를 기존 `Song.tjNumber`/`kyNumber` 에 backfill (덮어쓰기 아님, 빈 필드만 채움).

## 3) 요구사항

### 기능 요구사항

- [ ] 곡번호 수집 방식 3종(크롤링 / 공개 데이터·API / 수기)의 장단점·신선도·유지보수 비용을 §5-2 에 박제한다.
- [ ] TJ/금영 사이트의 약관·robots.txt·저작권·DB제작자권 리스크를 §5-3 에 판정(채택/비채택 근거 포함)한다.
- [ ] v0.2 pivot 과의 정합성 결론을 §5-1 + §9 에 명문화한다.
- [ ] 곡번호 ↔ 곡 매칭의 멱등 규칙(빈 필드만 backfill, 운영자 수정값 보존)을 정의한다.
- [ ] 채택안에 따른 단계적 로드맵(§6)과 단계 진입 게이트를 정의한다.

### 비기능 요구사항

- **합법성 우선 (비타협)** — robots.txt / 약관이 자동 수집을 금지하는 출처는 자동 크롤링 대상에서 제외. TJ/금영 곡목은 운영자 수기 참고를 default 로 한다 ([[song-catalog-expansion]] §5-3 기조 상속).
- **저작권/DB권 안전** — 노래방 곡목 DB 의 *편집·배열* 은 한국 저작권법상 DB제작자 권리(제2조 19호·제93조) 대상일 수 있다. **전체 곡목의 체계적 복제·대량 추출은 금지**. 곡번호는 개별 사실 데이터지만 대량 자동 추출은 DB권 침해 소지가 있어 §5-3 판정에 따른다.
- **곡번호 정확도** — 잘못된 곡번호는 노래방 현장에서 직접 사용성을 해치므로(엉뚱한 곡 예약), confidence 낮은 매칭은 노출 전 운영자 검수 필수.
- **외부 호출 최소·rate limit 준수** — (자동 경로 채택 시) 사이트 부하 회피를 위한 호출 간격·캐싱·User-Agent 식별 의무.
- **관측성** — 수집 단계별 성공/실패/skip/검수대기 카운트 로깅. 곡 메타 외 PII 없음.
- **가사/원본 audio 무단 복제 금지** — 곡번호(사실 식별자)만 대상. 가사·음원·앨범 이미지는 저장하지 않는다 (CLAUDE.md §4 보안).

## 4) 범위 / 비범위 (중요)

### 포함

- 노래방 곡번호(`tjNumber`/`kyNumber`) 자동 수집의 방식 비교·합법성 판정·정합성·도메인 영향·로드맵.
- 곡번호 ↔ 곡 매칭/정규화/멱등 규칙 설계.
- (채택 시) 곡번호 수집 파이프라인 아키텍처.

### 제외 (Out of Scope)

- **곡 일반 메타데이터(제목/아티스트/연도/장르/식별자) 수급** — [[song-catalog-expansion]] (MusicBrainz CC0) 책임. 본 spec 은 곡번호 차원만.
- **음역대/key/tempo 수급** — [[song-self-analysis-pipeline]] 자체 분석 책임. 외부 미제공.
- **TJ/금영 전체 곡목의 대량 미러링·재배포** — 저작권/DB권 리스크로 **명시적 비채택** (§5-3).
- **가사/음원/MR 반주 데이터 수집** — 저작권 침해. 절대 비채택.
- **노래방 예약/송출 연동(기기 제어)** — 별 제품 영역. 본 spec 무관.
- **신규 영속 엔티티 도입** — 곡번호는 기존 `Song.tjNumber`/`kyNumber` 컬럼으로 표현. 출처 추적은 §5-4 후보(미확정).

## 5) 설계

### 5-1) pivot 정합성 — 결론 (핵심)

**긴장 명시**:
- v0.2 pivot ([[project-self-analysis-pivot]], 2026-05-21): 방대한 외부 catalog ingest 폐기 → 큐레이션 + 자체 분석. **품질 > 방대함**.
- directive (#1496 후속, 2026-06-03): 노래방 곡목을 **자동 수집**해 곡 데이터를 늘리고 싶다.

**재검토 결론 — 곡번호는 [[song-catalog-expansion]] §5-0 의 "후보 풀 확장" 결론과 같은 축에 놓인다**:
- pivot 이 폐기한 것은 ① 방대 저품질 일괄 ingest, ② 추천 핵심 신호(음역대)의 외부 의존이다. 노래방 곡번호는 **둘 다 아니다** — 곡번호는 추천 랭킹 신호가 아니라 *이미 추천된 곡을 현장에서 입력하기 위한 편의 식별자* 다.
- 따라서 곡번호 수급은 pivot 과 충돌하지 않는다. 단, **수단(크롤링)** 이 합법성 게이트를 통과해야 한다 — 이는 pivot 이 아니라 §5-3 법적 판정의 문제다.
- **결론**: 곡번호는 (a) 후보 풀에 들어온 곡에 한해, (b) **합법 경로로만** 채운다. 곡번호 자체를 늘리려 곡 수를 방대하게 부풀리지 않는다 — 곡 풀 규모는 [[song-catalog-expansion]] §5-0 단계(100→~300)를 따르고, 본 spec 은 그 풀의 곡번호 *충실도* 만 책임진다.

### 5-2) 수집 방식 비교 (크롤링 vs 공개 데이터·API vs 수기)

| 방식 | 데이터 신선도 | 유지보수 비용 | 합법성 | 장점 | 단점 |
|---|---|---|---|---|---|
| **A. 자동 크롤링 (TJ/금영 웹 스크래핑)** | 높음(실시간 신곡 반영) | **높음** — DOM 구조 변경·IP 차단·캡차에 취약, 지속 보수 필요 | ⛔ 리스크 큼 (§5-3) | 곡번호 커버리지 최대 | 약관/robots.txt/DB권 위반 소지, 차단 취약, 정확도 검증 부담 |
| **B. 공개 데이터셋 / 공식 API** | 출처 갱신 주기에 의존 | 낮음(있다면) | ✅ 출처 약관 따름 | 합법·안정 | **존재 여부 불확실** — 공식 오픈 API 확인 필요(§8 Q1). 부재 시 선택 불가 |
| **C. 수기 큐레이션 (운영자 + AI 1차 제안)** | 낮음(운영자 처리량에 연동) | 중간(인력) | ✅ 완전 합법 | 정확도 최고(검수 내장), pivot 정합 | 곡번호 커버리지 느림, 규모 한계 |

**1차 권고**: **C(수기) 를 default 로 유지**하고, **B(공식 API/공개 데이터) 존재 여부를 조사(§8 Q1)** 해 확보 시 보조 채택한다. **A(크롤링)은 §5-3 법적 판정상 default 비채택** — B 가 부재하고 곡번호 수요가 큰 경우에 한해, 법적 검토를 통과한 *제한적·조건부* 경로로만 재론(§8 Q2).

### 5-3) 외부 연동 — TJ/금영 합법성 판정 (핵심)

> ⚠️ 본 절의 약관·robots.txt 항목 일부는 **시점 확인이 필요한 사실**이다. 단정 대신 리스크 프레임으로 제시하고, 자동 경로 채택 직전 운영자/법률 확인을 §8 오픈 질문으로 강제한다.

| 출처 | 데이터 | 약관 / robots.txt | 저작권·DB권 | 판정 |
|---|---|---|---|---|
| **TJ미디어 (태진) 곡목** | 곡번호, 제목/아티스트 | 사이트 ToS 상 자동 수집/상업적 재사용 제한 가능성 + robots.txt 크롤 disallow 통상 — **확인 필요(§8 Q1)** | 곡목 전체 = DB제작자권(저작권법 §93) 대상 가능. 개별 곡번호는 사실이나 **체계적 대량 추출**은 침해 소지 | ⛔ **자동 크롤링 default 비채택** — 수기 참고만 |
| **금영 (KY) 곡목** | 곡번호, 제목/아티스트 | 위와 동일 리스크 — 확인 필요 | 위와 동일 | ⛔ **자동 크롤링 default 비채택** — 수기 참고만 |
| **공식 오픈 API / 공공데이터** | 곡번호(제공 시) | 해당 약관 준수 | 출처 라이선스 따름 | ✅ **존재 시 채택** — §8 Q1 조사 결과에 따름 |
| **사용자 기여(UGC)** | 곡번호 제보 | 신뢰도 검증 필요 | — | ⏸ v0.4 후보 ([[song-curation-seed-100]] §4-1 경로 재사용) |

**핵심 판정**:
- **자동 크롤링은 default 비채택** — TJ/금영 곡목 DB 의 체계적 복제는 (i) 사이트 약관 위반, (ii) 한국 저작권법상 DB제작자 권리(편집·배열의 상당 부분 복제·전송 금지, §93) 침해, (iii) robots.txt 무시 시 부정경쟁/업무방해 소지가 중첩된다. [[song-catalog-expansion]] §5-3 의 TJ/금영 ⛔ 판정과 **일관**.
- **합법 경로 우선순위**: ① 공식 API/공개 데이터(존재 확인) → ② 운영자 수기(개별 곡 검색·전사, 사실 데이터의 소량·비체계적 활용) → ③ 사용자 기여(v0.4).
- **크롤링 재론 조건(있다면)**: 곡번호가 *사실 정보* 라는 점 + robots.txt 미금지 + 약관 미금지 + rate limit·User-Agent·캐싱 준수 + 전체 곡목 미러링 아님(필요 곡만 소량 조회) — **이 모두를 법률 검토가 확인**한 경우에만 조건부. 본 spec 은 이를 §8 Q2 로 보류하고 default 로 채택하지 않는다.

### 5-4) 도메인 모델 영향

- **신규 엔티티/마이그레이션 없음** — 곡번호는 이미 `Song.tjNumber String(16)` / `Song.kyNumber String(16)` (06-domain-model.md §5-2) 로 존재.
- **`metadataSource` 영향 없음** — 곡번호 backfill 은 곡의 1st-class 출처(`MANUAL_SEED`/`AUDIO_ANALYSIS`)를 바꾸지 않는다. 곡번호는 곡 메타의 부분 필드일 뿐 출처 권위 차원과 직교.
- **신규 도메인 용어 후보** (구현 PR 에서 `06-domain-model.md §4-1` 등재 의무 — 채택 시에만):

| 한국어 | 영어 (코드) | 정의 |
|---|---|---|
| 노래방 곡번호 | KaraokeNumber | TJ(`tjNumber`)/금영(`kyNumber`) 노래방 기기의 곡 식별 번호. `Song` 의 두 컬럼으로 표현되는 사실 식별자. 추천 랭킹 신호 아님 — 현장 입력 편의용. |
| 곡번호 출처 | KaraokeNumberSource | (후보) 곡번호 수급 경로 추적 enum — `MANUAL`(운영자 수기) / `OFFICIAL_API`(공식 출처) / `USER_CONTRIBUTION`. 영속 필요성은 §8 Q3 으로 보류 — 1차는 미도입(곡번호 자체만 저장). |

> 곡번호 출처 추적(`KaraokeNumberSource`)을 별 컬럼으로 둘지는 §8 Q3. 1차는 **컬럼 추가 없이** 기존 두 필드만 backfill 하는 것을 권고(마이그레이션·보호 영역 변경 회피).

### 5-5) 파이프라인 아키텍처 (B 또는 조건부 A 채택 시)

> default(C 수기)에서는 별 파이프라인 불요 — 운영자가 시드/임포트 JSON 의 곡번호 필드를 채우면 기존 `SongSeedLoader`/임포트 멱등 경로가 적재한다. 아래는 **합법 자동 경로(B/조건부 A)가 확보됐을 때**의 아키텍처.

```
[곡번호 NULL 인 Song 목록 조회]  (후보 풀 = song-catalog-expansion 가 채운 곡들)
        ↓
[수집 단계] 합법 출처(공식 API / 조건부 조회) 에 (title, artist) 질의
        ↓ rate limit + User-Agent + 캐싱 준수
[정규화 단계] 곡번호 형식 표준화(숫자 문자열, 좌측 0 보존), 곡명 표제어화(공백/특수문자/괄호 부제 정규화)
        ↓
[매칭·중복 제거 단계] (title, artist) 정규화 키로 Song 매칭
        ↓ 동명이곡/리메이크/라이브 → confidence 산정
[멱등 적재 단계] tjNumber/kyNumber 가 NULL 인 곡만 backfill (운영자 수정값·기존값 보존)
        ↓ confidence 낮음 → 운영자 검수 큐
[추천/검색/카탈로그가 곡번호와 함께 곡 노출]
```

- **배치 주기**: 곡 풀이 천천히 늘므로 상시 cron 불요. **곡 풀 확장 PR 후 1회성 트리거 + 운영자 수동 실행**(임포트 배치와 동일 트리거 모델, [[song-catalog-expansion]] §5-4).
- **멱등성**: (title, artist) 정규화 키 + "빈 필드만 backfill" 규칙. 재실행 시 row 불변·기존 곡번호 불변.
- **실패 격리**: 매칭 실패/모호 곡은 skip + 검수 큐 적재(전체 배치 abort 금지) — 임포트 스캐폴드 패턴 재사용.

### 5-6) 프론트엔드 화면

- 범위 외. 기존 곡 카드/검색 결과에 곡번호가 채워져 노출될 뿐 (FE 변경 없음 — 표시 컴포넌트가 이미 nullable 곡번호를 다룬다고 가정, 미확인 시 [[song-search-and-filter]] 와 cross-ref).
