# v0.3 마일스톤 Roadmap (초안)

> v0.2 거의 마무리(자체 분석 PoC + 좋아요/북마크 + PWA + Discord daemon 등) 시점에서 정리한 **v0.3 후보 백로그 초안**.
> 본 문서는 가시화 목적이며, v0.2 release 직전/직후 사이클에서 우선순위·spec 작성 여부를 한 번 더 확정한다.
> 우선순위는 `P1(필수) / P2(권장) / P3(보류 가능)`.

## 0) v0.2 → v0.3 컨텍스트

- v0.2 메타 전략: 자체 곡 분석 + 큐레이션 100곡 + 좋아요/북마크 영속화 + 음역대 자동 측정 (Vanido 영감).
- v0.3 메타 가설: **"피드백 누적 → 추천 품질 향상 + 사용자 컨텍스트 확장"**. v0.2에서 깐 feedback BC 데이터를 실제 추천 알고리즘에 반영하고, 사용자 음역대/취향 변화를 시간축으로 추적한다.
- 결정 미정: 노래방 곡번호(TJ/금영) 데이터 정합 방식, 정식 사용자 계정 전환 시점, 운영 호스팅 위치(현재 로컬/dev 위주).

## 1) v0.3 후보 백로그

### 1-1) [P1] 추천 알고리즘 v2 — ML 가중치 + audio features 매칭 활성화
- 출처: v0.2 `recommendation-history-and-feedback.md` 머지 후 feedback BC 데이터 누적.
- 작업: 사용자별 좋아요/북마크/dismiss 시그널을 입력으로 추천 점수 가중치 튜닝. 자체 분석 결과 `key/tempo`를 매칭 룰에 활성화(현재는 음역대만 매칭).
- 의존: v0.2 1-7(피드백 영속화) 머지 + 1-1(자체 분석 PoC) 60% 달성. `recommendation-algorithm-v1.md` → `v2` 신규 spec 필요.
- 예상 사이클: be 3 + spec 1 + ADR 1 (`0011 추천 알고리즘 v2 시그널·가중치`).
- 후속 ADR 후보: `0011 추천 알고리즘 v2 시그널·가중치`.

### 1-2) [P1] 사용자 음역 발전 추적 (Yousician 영감)
- 출처: 신규. 음역대 자동 측정(v0.2 1-11)이 1회성 측정에 그쳐, 시간축 발전을 보여주지 못함.
- 작업: 측정 결과를 `VoiceRangeSnapshot(userId, lowMidi, highMidi, measuredAt)` row로 영속화. `/me/voice-range/history` 응답 + fe 그래프(주/월 단위 추이).
- 의존: v0.2 1-11(음역대 자동 측정 B/C/D phase) 완료 + 사용자 식별(현 익명 세션이면 device-scoped로 시작 → 1-8 사용자 계정 후 user-scoped로 마이그레이션).
- 예상 사이클: be 1 + fe 1 + spec 1.

### 1-3) [P2] Spotify Audio Features 통합 (자체 분석 보강)
- 출처: v0.1 백로그 #69(보류 결정). v0.3에서 자체 분석 결과 검증·보강용으로 재검토.
- 작업: Spotify API에서 `danceability/energy/valence/acousticness` 등 보조 features 가져와 자체 분석 결과와 cross-check. ADR 0006(자체 분석 우선) 정합 유지 — Spotify는 **보강만**, primary 대체 금지.
- 의존: v0.2 1-1(자체 분석) PoC 60% 달성. Spotify dev account.
- 예상 사이클: be 1 + ADR 1 (`0012 Spotify Audio Features 보강 정책`).
- 리스크: Spotify API rate limit, 한국 곡 매칭률 변동.

### 1-4) [P2] 노래방 곡번호 TJ/금영 정식 보강
- 출처: v0.2 §3 "TJ/금영 카탈로그 보강" 이월. 사용자 결정 대기 중.
- 작업: 큐레이션 100곡 + 자체 분석 결과 곡에 대해 TJ/금영 곡번호 매칭 데이터 PR. 추천 응답에 `tjNumber/kyNumber` 노출.
- 의존: 데이터 출처(공식 API 없음 → 수동 크롤/사용자 입력) 결정 필요. **사용자 결정 후 진행** (이슈 등록 시점에 사용자에게 출처 확인).
- 예상 사이클: be 1 + 데이터 PR 1.
- 미해결: 라이선스/저작권 검토 — ADR 후보 `0013 노래방 곡번호 출처·라이선스 정책`.

### 1-5) [P2] 사용자 계정 (현 익명 세션 → 정식 계정 옵션)
- 출처: v0.2까지 익명 device-scoped 운영. 음역 추이(1-2)·피드백(v0.2 1-7) 누적이 늘수록 계정 필요성 증가.
- 작업: OAuth(Google/Kakao 등) 로그인 옵션 + 익명 세션 → 정식 계정 migration. 익명 사용은 그대로 유지(opt-in 계정).
- 의존: 인증 전략 ADR + spec 선행. 1-2 음역 추이는 device-scoped로 시작해 계정 도입 후 user-scoped로 이전.
- 예상 사이클: be 2 + fe 1 + spec 1 + ADR 1 (`0014 사용자 계정 인증 전략`).
- 보호 영역: `application*.yml`(OAuth client 설정), `**/db/migration/**`(User 테이블 확장).

### 1-6) [P2] 운영 관측성 (Sentry + Grafana/Prometheus)
- 출처: v0.2까지 로컬 로깅 + Discord 알림 중심. 운영 배포 결정 시 관측성 필수.
- 작업: Sentry(error tracking) + Prometheus exporter + Grafana dashboard. `10-observability.md` 룰을 실제 인프라로 연결.
- 의존: 운영 배포 결정(현재 미정). v0.2 1-9 Flyway 머지 후 배포 결정과 한 패키지로 진행.
- 예상 사이클: be 1 + infra 2.
- 보호 영역: `**/application*.yml`, `docker-compose*.yml`, `.github/workflows/**` 다수.

### 1-7) [P3] 소셜/공유 (Smule 영감)
- 출처: 신규. 추천 결과·음역 추이·연주(?) 공유 기능.
- 작업: 사용자가 추천 카드/음역 그래프를 외부(카카오톡/인스타 스토리)로 공유. **공유 콘텐츠 한정**(녹음/연주 업로드 미포함 — Smule full 기능은 v0.4+).
- 의존: 1-5 사용자 계정(공유 주체 식별) + UX 디자인.
- 예상 사이클: fe 2 + be 1 (공유 메타 endpoint).
- 리스크: 익명 사용자 공유 정책 미정.

### 1-8) [P3] 다국어 (i18n)
- 출처: 신규. 현재 ko 단일.
- 작업: fe i18n 인프라(next-intl 등) + ko/en/ja 우선. be 응답 메시지(`matchReason` 등)는 ko 고정 유지 또는 별도 ADR.
- 의존: 해외 사용자 트래픽 시점 결정. **현 시점 P3** — 한국 시장 검증이 먼저.
- 예상 사이클: fe 2 + ADR 1 (`0015 i18n 적용 범위`).

### 1-9) [P3] 후속 정비 백로그 v0.3 묶음
- v0.2 1-10과 동일 패턴. idle 사이클 흡수.
- 후보: v0.2 진행 중 발견된 컨벤션 위반·테스트 누락·문서 sync 등.
